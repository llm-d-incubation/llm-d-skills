# Connectivity Verification Instructions

Instructions for the opt-in connectivity test of Step 5 in the main workflow. The test sends inference requests through the llm-d router, which populates the KV cache of the model servers. Only follow these steps after the user has agreed.

## How the endpoint is reached

Both modes expose a cluster-internal address, so the guide's tests run from a short-lived pod inside the cluster (`kubectl run curl-test ...`). No port-forward is required.

| Mode | Endpoint source (from `guide.yaml`) | Address |
|---|---|---|
| `standalone` | `verify.endpoint.standalone` | ClusterIP of service `${GUIDE_NAME}-epp`, port 80 |
| `gateway` | `verify.endpoint.gateway` | `status.addresses[0]` of Gateway `llm-d-inference-gateway` |

For access from the operator's machine use a port-forward to the same service or gateway:

```bash
kubectl port-forward -n ${NAMESPACE} svc/${GUIDE_NAME}-epp 8000:80     # standalone mode
```

## Step 1: Generate the verification script

Create `deployments/verify-connectivity-${NAMESPACE}.sh` from the guide's own steps plus a model listing:

```bash
{
  echo "# Connectivity verification generated by deploy-llm-d on $(date -u +%Y-%m-%dT%H:%MZ)"
  echo "# guide: ${GUIDE_DIR#${LLMD_PATH}/}  namespace: ${NAMESPACE}  mode: ${MODE}"
  ${GUIDE_PY} emit ${GUIDE_DIR} env verify.endpoint.${MODE} "${EMIT_VARS[@]}"
  cat <<'EOF'

# === /v1/models (read-only; confirms the served model name) ===
kubectl run curl-models --rm -i --restart=Never --image=${CURL_TEST_IMAGE} --namespace="${NAMESPACE}" \
  --env="IP=${IP}" -- /bin/sh -c 'curl -sS "http://${IP}/v1/models"'
EOF
  ${GUIDE_PY} emit ${GUIDE_DIR} env verify.tests.request "${EMIT_VARS[@]}" | sed -n '/^# === verify.tests.request ===/,$p'
} > deployments/verify-connectivity-${NAMESPACE}.sh
chmod +x deployments/verify-connectivity-${NAMESPACE}.sh
```

`verify.tests.request` is the guide's canonical completion request. The `env` block of the first `emit` provides `IP`, `MODEL`, and `CURL_TEST_IMAGE` for the following commands. Some guides name the request test differently (`verify.tests.served_model`, `verify.tests.request.routing`); take the first `test` entry of the Step 3 summary that sends a single completion request.

Show the full script content to the user.

## Step 2: Ask for permission to execute

Ask the user, with the assistant's question tool, whether to run `deployments/verify-connectivity-${NAMESPACE}.sh`. State that it sends one completion request to the stack. Do not execute without an explicit yes.

## Step 3: Execute only after approval

```bash
bash deployments/verify-connectivity-${NAMESPACE}.sh
```

Expected results:

- `/v1/models` returns a JSON document whose `data[].id` contains `${MODEL}`.
- The completion request returns HTTP 200 with a `choices[0].text` field.

If the model name differs from `${MODEL}`, use the returned name in further requests and record the difference in the deployment summary.

If the user declines, tell them the script is ready to run manually.

## Step 4: Optional guide-specific tests

Each guide ships further `verify.tests.*` step lists that exercise its mechanism (`shared_prefix` and `pod_metrics` for prefix-cache affinity, `pd_requests` for prefill/decode, `offload_metrics` for tiered caches). They send more traffic. Offer them only when the user wants to confirm the routing behavior, and emit them the same way:

```bash
${GUIDE_PY} emit ${GUIDE_DIR} env verify.endpoint.${MODE} verify.tests.<name> "${EMIT_VARS[@]}" | bash
```

## Step 5: Local smoke test (alternative)

For a check from the operator's machine, the upstream smoke test works against a port-forwarded endpoint and needs only `curl` and optionally `jq`:

```bash
kubectl port-forward -n ${NAMESPACE} svc/${GUIDE_NAME}-epp 8000:80 &
bash ${LLMD_PATH}/docs/operations/validation/smoke-test/healthcheck.sh -e http://localhost:8000 -m "${MODEL}"
kill %1
```

## Critical Rules

- Step 2 cannot be skipped: no request is sent without approval.
- Always show the script content before asking to execute it.
- Do not read `kubectl top` or GPU utilization as proof of correctness; the HTTP responses above are the acceptance criteria.
